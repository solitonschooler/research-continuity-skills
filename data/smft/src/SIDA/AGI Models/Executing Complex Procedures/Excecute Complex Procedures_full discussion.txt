# ENIAC / IAS Possession: Topology × Strong-Attractor Prompting for Executing Complex Procedures

*(Author Manual — for an advanced LLM that will write prompts for another LLM to execute)*

---

## 0) Calc-Pad (why this works, in one page)

**Goal.** Make the executor-LLM behave like a step-faithful executor (plan → execute → self-audit), without writing real code.

**Mechanism (textual VM).** Constrain the executor’s output channel to a **minimal instruction set (OPCODES)**, a **single source-of-truth STATE ledger**, **phase gates** (P0→P3), **invariants + rollback**, and **self-audit**. This turns freeform language into a low-entropy “machine code” ritual.

**Two modes.**

* **ENIAC-mode**: **no branches**; fully unrolled plan (“wiring”). Safest whenever the whole procedure can be expanded.
* **IAS-mode**: **minimal branching** with an auditable **Program Counter** (PC) and tiny jump set (JZ/JNZ/JMP). Use when a few conditions are unavoidable.

**What this gives you.** Deterministic, auditable step traces; cross-model reproducibility; graceful failure (rollback) instead of narrative drift.

---

## 1) Strong-Attractor Core Principles (never skip)

1. **Zero-ambiguity vocabulary.** Actions must come from an **OPCODE whitelist**; no synonyms.
2. **Structural contract.** Four phases (P0 Feasibility/Spec → P1 Plan/Program Freeze → P2 Run/Trace → P3 Verify/Audit) with **GATE\_OK** to cross; **STATE ledger**; **invariants**; **per-step CHECK**; **rollback/stop** on violation.
3. **Standardized algorithms.** Prefer proven shortest/stablest templates (and include shortcuts when known). The attractor is linguistic *and* algorithmic.

---

## 2) When to choose ENIAC vs IAS (and when to upgrade)

**Pick ENIAC-mode** if:

* The procedure can be **fully unrolled** (no decisions required),
* Estimated steps ≤ **20**,
* You need strongest reliability / cross-model replay.

**Pick IAS-mode** if:

* You need **2–5 conditional jumps**,
* You still want a compact, auditable control flow.

**Auto-upgrade triggers** (start stricter or switch during run):

* Estimated steps > **20**, or high-risk domain (finance, legal, medical),
* Arithmetic/lookup heavy (then add structured outputs/tools),
* Early-warning signs (plan drift, invariant violations, repeated replans).

## 4) ENIAC-mode Capsule (drop directly into `EXECUTION_PROMPT`)

```yaml
ROLE: ENIAC-mode Self-Discipline Attractor (no branches; plan = wiring)
PHASES: 
  P0 SPEC → P1 PLAN (freeze) → P2 EXECUTE (trace) → P3 AUDIT
  Cross-phase only after printing: GATE_OK=true
OPCODES (only; no synonyms): 
  # Replace with domain verbs, or keep abstract register ops
  SET k:=v | MOV i→j | ADD k→j | SUB k→j | ZERO k | HALT
STATE (single source of truth): 
  T(step), REG{R0..R9 or named}, TAPE(plan), LOG(append-only)
INVARIANTS: 
  - Atomic commits
  - Bounds respected for all REG/state fields
  - Each execution step must consume exactly one TAPE item
P1 PLAN (freeze): 
  - Numbered steps: "#k ACT(OPCODE) → EXPECTED_STATE"
  - Print PLAN_LEN and PLAN_SIGNATURE (hash of OPCODE tokens)
P2 TRACE (one row per step): 
  - t | PRE(STATE) | ACT | POST(STATE) | CHECK=TRUE/FALSE | LOG(Δ)
FAILSAFE: 
  - On CHECK=FALSE ⇒ SAFE: ROLLBACK last commit & STOP(ERROR)
OUTPUT ORDER (strict):
  1) P0 SPEC 
  2) P1 PLAN (PLAN_LEN, PLAN_SIGNATURE) 
  3) P2 TRACE 
  4) P3 AUDIT {match(plan_vs_trace), invariants_ok, confidence∈[0,1]}
```

**When to use:** fully unrolled recipes, checklists, puzzles with known shortest templates, data migration scripts, deterministic workflows.

## 5) IAS-mode Capsule (drop directly into `EXECUTION_PROMPT`)

```yaml
ROLE: IAS-mode Self-Discipline Attractor (stored-program; auditable PC)
PHASES:
  P0 FEASIBILITY → P1 PROGRAM (freeze) → P2 RUN (fetch→decode→execute) → P3 VERIFY
  Cross-phase only after printing: GATE_OK=true
REGISTERS & STATE (single source of truth; atomic commits):
  PC, ACC, MEM[0..M-1], FLAGS{Z,N}
OPCODES (only; no synonyms):
  LOAD a | STORE a | ADD a | SUB a | CMPZ | JZ a | JNZ a | JMP a | NOP | HALT
INVARIANTS:
  - PC must be a valid address or HALT
  - MEM addresses must exist; values within bounds
  - FLAGS set consistently with operations
RUN_TABLE (one row per instruction):
  t | PRE{PC,ACC,FLAGS} | IR | EFFECT | POST{PC,ACC,FLAGS} | CHECK=TRUE/FALSE
FAILSAFE:
  - On CHECK=FALSE ⇒ SAFE: ROLLBACK last commit & STOP(ERROR)
OUTPUT ORDER (strict):
  1) P0 FEASIBILITY
  2) P1 PROGRAM LISTING (PROGRAM_LEN, PROGRAM_SIGNATURE)
  3) P2 RUN_TABLE
  4) P3 VERIFY {goal_ok, invariants_ok, confidence∈[0,1]}
```

**When to use:** small scheduling/assignment with a few constraints, compliance checks with 2–5 conditions, light ETL branching, simple rule engines.

## 7) Mini Examples (for the author to pattern-match)

### 7.1 ENIAC — Water Jugs (A=6, B=10, target A=4)

* **OPCODES**: `FillA, FillB, EmptyA, EmptyB, PourA→B, PourB→A, HALT`
* **STATE**: `STATE = (xA:int[0..6], xB:int[0..10])`
* **INVARIANTS**: `0≤xA≤6; 0≤xB≤10; integer volumes; no overflow`
* **P1 PLAN (shortest 4 steps)**
  `#1 FillB → (0,10)`
  `#2 PourB→A → (6,4)`
  `#3 EmptyA → (0,4)`
  `#4 PourB→A → (4,0)`
* **P2 TRACE row format**: `t | PRE(xA,xB) | ACT | POST(xA',xB') | CHECK`
* **P3**: `FINAL=(4,0); goal_ok=true; invariants_ok=true; confidence=0.95`

### 7.2 IAS — 3-task Scheduling with one conflict rule

* **Task**: schedule A,B,C into time slots; constraint: **A and C cannot overlap**; each has duration and deadline.
* **OPCODES**: `LOAD job`, `CMPZ slot_free`, `JZ place`, `STORE schedule`, `JMP next`, `HALT`
* **STATE\_SCHEMA**: `PC, ACC={current_job}, MEM={slots[], durations[], deadlines[], schedule[]}, FLAGS{Z}`
* **INVARIANTS**: no overlap; within deadlines; “A//C not parallel” always true.
* **RUN\_TABLE**: per instruction row with PRE/IR/EFFECT/POST/CHECK; P3 prints `schedule[]`, `violations=0`, confidence.

## 8) Cost & Tiering (use the right torque)

* **Tier 0 (soft attractor)**: lightweight headings + minimal vocabulary (fast ideation; ≤8 steps).
* **Tier 1 (ENIAC)**: unrolled plan, per-step trace and checks (8–20 steps; reproducible).
* **Tier 2 (IAS + structure/tools)**: minimal branching + JSON/grammar + tool calls (long chains; arithmetic/lookup; high risk).

**Rule of thumb.** If you *can* ENIAC, **do ENIAC**. If you *must* branch, **IAS** with the smallest jump set. If arithmetic/verification is heavy, keep the VM as planner/auditor and offload compute/search to tools with **structured outputs/grammar**.

---

## 9) Optional Add-Ons (use when needed)

* **Early-Warning Indices (EWI)** for drift: `plan_drift_rate`, `replan_AR1`, `invariant_violations`. Breach ⇒ “Stabilize”: deepen basin / reduce noise / retune thresholds.
* **Structured Outputs / Grammar**: enforce JSON/CFG when downstream systems consume outputs.
* **Tool-Call Stubs**: clearly mark where to dispatch math/lookup to a calculator/DB/search; VM remains in control of planning and auditing.

### One-liner summary (to remember)

**Make the executor LLM a textual VM.** Lock vocabulary (OPCODES), lock state (single ledger), lock rhythm (P0→P3 with gates), lock safety (invariants + rollback), and—when possible—**fully unroll** with ENIAC. If you must branch, use IAS with the smallest, auditable jump set.






The 3 prompts in 3,4,5 can be used independently as 3 separate prompts?






Short answer: **Yes**—they can be used independently, but they serve **different roles**:

* **#3 (Generator Template)** → *Author prompt*. Use this with an “author LLM” to **produce** a final execution prompt. It is **not** meant to execute the task itself.
* **#4 (ENIAC Capsule)** → *Executor prompt*. Paste this (with your task bindings) into any advanced LLM to **run a fully unrolled, no-branch** procedure.
* **#5 (IAS Capsule)** → *Executor prompt*. Paste this (with your bindings) to **run minimal-branching** procedures with an auditable PC.

Here’s how to use each on its own:

1. \#3 by itself (Author-only)

* Provide `<<TASK_SPEC>>`, `<<DATA_SHAPES>>`, `<<RISK_LEVEL>>`, `<<EST_STEPS>>`, etc.
* It returns **one block** named `EXECUTION_PROMPT`.
* Copy that block into a **separate** LLM session (or next message) to execute.

2. \#4 by itself (Direct ENIAC execution)

* Before the capsule, add a small header with your bindings:

  * `OPCODE_SET = [...]` (no synonyms)
  * `STATE_SCHEMA = {... fields, bounds ...}`
  * `INVARIANTS_LIST = [...]`
  * `TASK_SPEC = ...`
* Then paste the **ENIAC capsule** and let the model Plan → Execute → Audit.

3. \#5 by itself (Direct IAS execution)

* Same as #4, but choose IAS when you need a few conditional jumps.
* Provide minimal jump logic via the given `OPCODES` and the `RUN_TABLE`.

Tips / gotchas:

* Don’t mix roles: #3 **writes** the prompt; #4/#5 **run** the prompt.
* If you use a single LLM to both author and execute, do it in **two turns** (copy-paste the produced `EXECUTION_PROMPT`) to avoid self-mutation.
* For #4/#5, **fill all placeholders** (OPCODES, STATE, INVARIANTS); leaving them generic weakens the attractor.
* Rule of thumb: **If you can ENIAC, do ENIAC**; otherwise IAS with the smallest jump set.
